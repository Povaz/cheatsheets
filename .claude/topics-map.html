Locate note

  • Direct ECS RunTask from the Django request path — no queue, no Celery, no in-process thread. The trigger view creates a frozen BulkBotJob (config snapshot + total) inside transaction.atomic(), dispatches AFTER commit so the row is visible before the task can start, and swallows dispatch errors to still return 201 (the failure is persisted on the job and surfaced by the poll endpoint). One Fargate task per job runs the same backend image with the command overridden to `manage.py run_bulk_valuations --job-id <uuid>`; the task definition ships a bare default so a stray launch exits with a usage error instead of running a batch. Ownership is enforced by conditional UPDATEs, not locks: the task ARN is written back with filter(status=QUEUED, task_arn__isnull=True).update(...) and a 0-row result immediately stop_task's the orphan; the heartbeat fuses touch + ownership check into one filter(status=RUNNING).update(updated_at=Now()). Recovery is lazy and read-path-driven (reclaim_inactive_jobs on both trigger and poll, INACTIVE_AFTER=60min); concurrency is a partial unique constraint over status in (queued, running) surfaced as 409. Infra: not an ECS service (no desired count / target group / autoscaling), own awsvpc ENI with no ingress and open egress, task role with zero policies, env via environmentFiles from S3. NOTE: as of the scan the implementation sits on branch feat/bulk-bot-ecs (worktree .claude/worktrees/bulk-bot-ecs/); only the contract test and design doc are on dev, so backend/location_intel/dispatch.py is not yet in the main checkout. Sheet angle = RunTask as a job runner, conditional-UPDATE ownership, lazy reclamation vs. a scheduler. Pairs with [[Background Jobs & Concurrency (async batch, atomic 409)]] and [[ECS / Fargate Services]]. UPDATE 2026-07-31: merged to dev — backend/location_intel/dispatch.py is now in the main checkout (the earlier feat/bulk-bot-ecs worktree caveat is resolved), and cicd-dev.yml gained a job that registers the BulkBot worker task definition, so the task-def is CI-managed rather than hand-registered. The worker itself is now bounded-parallel — see [[Bounded Concurrency (ThreadPoolExecutor, per-thread DB connections)]].

Locate note

  • UPDATE 2026-08-05: compute_simple_locations() in backend/basic/dao.py is a live lesson in aggregate self-reference. City centroids are ST_Centroid(ST_Collect(geocoords::geometry)), but hotels whose coordinates were BACKFILLED from that same centroid (geocoords_source = LOCATION) would double-count themselves and dampen the centroid once real coordinates arrive — so both ST_X/ST_Y aggregates gained a FILTER, plus a HAVING COUNT(*) FILTER (...) > 0 so a city whose only located hotels are LOCATION-sourced mints no Location row at all. The filter is deliberately geocoords_source IS DISTINCT FROM 'LOCATION', not = 'HOTEL': a NULL source means a legacy pre-tracking hotel that must still count, and the strict form returned centroid_x = NULL for pre-migration fixtures and broke CI. count(name) as hotels_number stays UNFILTERED, so LOCATION-sourced hotels remain city members for reporting while contributing zero spatial signal. Sheet angle = FILTER on aggregates, HAVING COUNT(*) FILTER, IS DISTINCT FROM vs = for nullable columns, and derived-data feedback loops. UPDATE 2026-08-06: the GDAL/GEOS library paths and headers were corrected for multi-arch (Apple Silicon vs x86 containers). GDAL_LIBRARY_PATH / GEOS_LIBRARY_PATH pinning is the single most common reason a GeoDjango project starts on one machine and not another — worth a line on the sheet.

  • Two search families run over a catalog of 783 tsfresh features per demand curve, both trying to beat an 8-dimensional hand-picked Fourier vector — and both failing, for instructive reasons. The univariate FILTER (tsfresh FRESH + Benjamini-Yekutieli FDR control) is useless on synthetic training curves: 527 of 777 candidates pass because generated curves are trivially separable and p-values tie at the numerical floor, its picks don't transfer to real labels, and its n_significant>=2 rule would discard three of the eight columns that make the baseline work — because scoring features one at a time cannot see that a weak coefficient is load-bearing beside the other seven. Locate note

  • A dense 371→256→64→8 autoencoder trained to reconstruct synthetic demand curves, its 8-dim code fed to the shipped RandomForest, loses to the hand-picked Fourier vector on every retraining (0.653 ± 0.047 vs 0.714 macro-recall) — and its sd from retraining alone is the widest noise floor measured. The cause is a DISTRIBUTION GAP, not capacity: it reconstructs held-out synthetic curves 22x better than the real corpus, so real cities sit 4-7x the within-cloud spacing off the learned manifold. Two clean decouplings fall out — PCA-8 reconstructs real curves better and classifies worse, and widening the code 8→32 improves reconstruction without moving the score: reconstruction fidelity is not discriminability. Adding labels makes it worse, not better (a supervised 371→8→5 net pins synthetic accuracy at 1.000 at every width 4..64 while real accuracy tops ~0.69 and one class collapses entirely) — no synthetic regulariser can close a synthetic→real gap. Separate, sharper result: every way of down-weighting the year boundary before the FFT costs real macro-recall monotonically in edge weight removed (core slice 0.654, raised-cosine 0.645, aggressive Hann 0.533, vs full-grid 0.714) because winter-peaking mountain/ski locations have their peak AT the year edges — so the 343-slot core window helps the similarity view and hurts classification.
