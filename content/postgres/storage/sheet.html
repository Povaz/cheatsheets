A cluster is a directory of ordinary files

Everything a PostgreSQL server owns lives under one directory — the data directory, PGDATA — called the cluster. Inside it: base/ holds one subdirectory per database, named by the database's OID; pg_wal/ holds the write-ahead log (the closing section of the next Sheet); global/ holds cluster-wide catalogs; plus the configuration files.

Each table and each index — collectively, each relation — is stored as its own file, named by a number (pg_class.relfilenode). Past 1 GB the file is cut into gigabyte segments (16986, 16986.1, …) to dodge platform file-size limits. Nothing exotic is happening: a table is an ordinary file you could point ls -l at.

psql
SELECT pg_relation_filepath('users');
 base/16384/16986        -- database OID 16384, relation file 16986

Every one of those files has the same internal shape: an array of fixed-size pages.

The 8 KB page

The page (8,192 bytes by default) is the unit of I/O — the server never reads or writes less than one. Its layout is a fixed choreography of three growing fronts:

  • A 24-byte header opens the page. Among its fields, pd_lower and pd_upper record where the free space starts and ends — the page's own accounting of how full it is.
  • An array of line pointers grows forward from the header — 4 bytes each, holding a tuple's byte offset, its length, and a couple of state bits.
  • Tuples — the rows themselves — stack backward from the page's end. New line pointers are allocated from the front, new tuples from the back; the free space is whatever remains between pd_lower and pd_upper, and the page is full when they meet.

Inside a tuple

A tuple is a 23-byte header, an optional null bitmap, then the column values in declaration order. The header is bookkeeping about the row version's life, not about your data:

  • t_xmin — the ID of the transaction that created this version.
  • t_xmax — the ID of the transaction that deleted it; zero while the version lives.
  • t_ctid — the address of this or the newer version of the row: when an update writes a replacement, the old version's t_ctid points forward to it, chaining versions together.
  • t_infomask + t_hoff — flag bits, and the offset where the user data starts.
  • The null bitmap — one bit per column — exists only when at least one column is NULL: absent columns cost bits, not bytes.

ctid: the address of a row

A row's address is ctid = (page, slot) — page number in the file, slot number in that page's line-pointer array. The address names the line pointer, never the tuple bytes: the pointer holds the current byte offset, so a tuple can move inside its page (defragmentation, cleanup) while every address pointing at it stays valid. That one level of indirection is deliberate, and the state bits make a line pointer more than an offset — it can also be unused, dead, or a redirect to another slot, states the Indexes Sheet spends heavily.

psql
SELECT ctid, id, email FROM users LIMIT 3;
  ctid | id |      email
 ------+----+------------------
 (0,1) |  1 | ada@example.com
 (0,2) |  2 | alan@example.com
 (0,3) |  3 | edsger@example.com

ctid is an address, not an identity: updates write new versions at new addresses, so it is valid only until the row next moves.

A heap has no order — and two maps beside it

A table's pages form a heap: a new row lands in whatever page has room, and nothing ever maintains any ordering. Space freed by dead rows is reused in place; the file itself rarely shrinks. Two questions this raises — where is there room? and which pages are settled? — are answered by two small bookkeeping files, the forks that live beside every table's main file:

ForkFileWhat it tracks
main16986the pages themselves — everything above
free space map16986_fsmfree space per heap page, one byte per page, organised as a tree whose upper levels hold the maximum of their children — so "find a page with ≥ N bytes free" costs a few page reads, not a table scan. Kept approximately current, mainly by VACUUM.
visibility map16986_vmone all-visible bit per heap page — "every tuple here is visible to every transaction". Set only by VACUUM, cleared by any write to the page. The Indexes Sheet turns this bit into index-only scans.
init16986_initunlogged relations only — the empty state restored after a crash.

TOAST: values too big for a page

A tuple cannot span pages, and the system wants at least four tuples per page — so when a row would exceed ~2 KB, TOAST (the oversized-attribute storage technique) steps in and shrinks it until it fits or nothing more can be gained:

1 · compresssqueeze the wide variable-length values (pglz or lz4) in place
2 · move outstill too wide? push the widest values into the table's companion TOAST table, chopped into ~2,000-byte chunks — four per page
3 · stubthe main tuple keeps an 18-byte pointer, whatever the value's true size
4 · read backchunks are fetched and reassembled transparently — and only when the query actually selects that column

Per column, four declared strategies bound what TOAST may do:

StrategyCompress?Move out-of-line?Default for
PLAINnonofixed-length types (int, timestamptz…)
MAINyesonly as a last resort—
EXTERNALnoyes— (faster substring ops on big text)
EXTENDEDyesyesmost variable-length types

The consequence worth keeping: a query over narrow columns never pays for the wide ones — "this row is 2 MB" usually means 18 bytes here, 2 MB somewhere else.

See it: pageinspect

Everything on this Sheet is inspectable from SQL. The pageinspect extension reads raw pages; heap_page_items lists every line pointer and tuple header on one — including versions no query can see any more:

psql
CREATE EXTENSION pageinspect;
SELECT lp, lp_off, lp_flags, lp_len, t_xmin, t_xmax, t_ctid
FROM heap_page_items(get_raw_page('users', 7));
 lp | lp_off | lp_flags | lp_len | t_xmin | t_xmax | t_ctid
----+--------+----------+--------+--------+--------+--------
  1 |   8064 |        1 |    121 |    812 |      0 | (7,1)
  2 |      5 |        2 |      0 |        |        |
  5 |   7808 |        1 |    128 |    951 |      0 | (7,5)

Reading it with this Sheet's vocabulary — lp_flags: 0 unused · 1 normal · 2 redirect · 3 dead:

  • lp1 — a normal line pointer: its tuple starts at byte 8064, created by transaction 812, never deleted, and t_ctid (7,1) points at itself: no newer version.
  • lp2 — a redirect: no tuple at all; lp_off holds the slot it forwards to (5). Every external address (7,2) still works.
  • lp5 — the live version lp2 forwards to, created by transaction 951.

How lp2 came to forward to lp5 — an update that stayed on its page — is the Indexes Sheet's HOT section. The bytes were here all along.
