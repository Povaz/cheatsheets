Indexes §03 — one SELECT walks the tree

Every walkthrough on this Sheet runs against the same fixture — read the Indexes Sheet first; each section here grounds exactly one of its sections.

the fixture — used by every example below
CREATE TABLE users (
  id         bigint PRIMARY KEY,   -- B-tree: users_pkey
  email      text UNIQUE,          -- B-tree: users_email_key
  last_login timestamptz           -- no index
);
-- ~1,000,000 rows

The tree first. A bigint leaf entry costs a few dozen bytes, so a leaf holds ~370 entries: 1M rows ≈ 2,700 leaf pages; one internal level of ~7 pages covers those; one root covers the internal level. Depth 3 — exactly the shape the walk below descends. The query:

psql
EXPLAIN SELECT email FROM users WHERE id = 424242;
 Index Scan using users_pkey on users
   Index Cond: (id = 424242)
  1. Read the root (index page 290 — one 8 KB page, virtually always in shared buffers). Binary-search its sorted separators: … 350000 · 700000 …. 424242 falls in (350000, 700000], and the downlink between those two separators names page 74.
  2. Read internal page 74. Its separators: … 421000 · 427000 …. 424242 falls in (421000, 427000] → downlink names leaf page 3151.
  3. Read leaf 3151. Binary-search its sorted (key, TID) entries → 424242 → (8191, 4).
  4. Read heap page 8191, follow line pointer 4 to the tuple, check its xmin/xmax against the snapshot, return email.

Total: 3 index pages + 1 heap page for one row in a million — and since the root and internal levels together are ~8 pages, steps 1–2 are almost never real I/O. Steady state: one or two actual page reads.

Indexes §06 — a split lands under a running reader

Leaf 3151 from the walk above covers (421000, 427000] — high key 427000 — and is currently full. Two sessions collide on it:

the two queries
-- session W (writer)
INSERT INTO users VALUES (424243, 'new@example.com', NULL);

-- session R (reader), concurrent
SELECT email FROM users WHERE id = 425500;
tW — INSERT 424243R — SELECT 425500
1reads parent page 74: downlink for (421000, 427000] → leaf 3151; releases its lock on 74
2descends the same way, write-locks leaf 3151: full — 424243 doesn't fit(about to read 3151)
3splits: entries above 424100 move to a new page 9001; 3151's high key := 424100, right-link := 9001; 424243 lands on 9001; locks releasedwaits only if it arrives during t3 itself — page locks last microseconds, and nothing above the leaf was locked
4posts separator 424100 + downlink to 9001 into parent 74read-locks 3151: 425500 > high key 424100 → the page split under me
5donefollows the right-link to 9001: 425500 ≤ high key 427000 → binary search → TID → heap → row returned

What the two B-link fields bought, in this trace:

  • Without the high key, R would have binary-searched 3151 at t4, found no 425500, and wrongly answered "no such row" — a correctness bug, not a slowdown. The high key is what tells R that the page's coverage shrank.
  • Without the right-link, knowing wouldn't help — R would have nowhere to go but back up through a parent that (until t4 completes) doesn't point to 9001 yet.
  • Without both, the classic fix is lock coupling: R holds 74's lock until it has locked 3151, and W's split must queue behind every reader in flight. Here neither session ever held more than one or two page locks, each for microseconds, and neither waited on the other's whole operation.
  • Readers that descend via the stale parent after t5 recover the same way — move right until the high key covers the key — so the parent update at t4 can afford to be lazy.

Indexes §07 — two sessions, one row, two truths

What "someone's snapshot may still need the old version" looks like in two terminals. Session A freezes its snapshot at t1 (under REPEATABLE READ, the whole transaction keeps it); session B updates and commits mid-flight:

tA — REPEATABLE READB — autocommit
1BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT last_login FROM users WHERE id = 42; → 2026-08-01 — snapshot frozen: "everything committed as of now, nothing after"
2UPDATE users SET last_login = now() WHERE id = 42; — as transaction 951: writes v2 at (7,5), stamps v1's xmax = 951; commits
3same SELECT → still 2026-08-01. It reads v1, sees xmax = 951 physically stamped — and ignores it: 951 is not in A's frozen snapshot, so the deletion hasn't happened for Anew query → SELECT sees v2: fresh snapshot, 951 committed
4COMMIT; then SELECT → v2, like everyone else

The same bytes, two verdicts — visibility is a function of (version header, snapshot), never of the version alone. You can watch the bytes:

run inside A at t3
SELECT ctid, xmin, xmax, last_login FROM users WHERE id = 42;
 (7,2) |  812 |  951 | 2026-08-01 …     -- v1: deleted, but not "for me"

Between t2 and t4, v1 must exist — in the heap and in every index — purely because A is still running. Only when A ends does v1 become dead to everyone: prunable, vacuumable. A long-running transaction is a promise the whole cluster keeps: nothing its snapshot can see may be cleaned anywhere.

Indexes §08 — three updates, one HOT

Same table, three updates of row id = 42, whose version v1 sits at (7,2). The row is ~100 bytes; the two conditions decide each fate:

UpdateIndexed column changed?Room on page 7?Outcome
SET last_login = now()no (last_login has no index)1.2 KB free ≥ 100 BHOT — zero index writes
SET last_login = now()no60 B free < 100 Bnot HOT — v2 lands on another page, so both indexes get new entries
SET email = 'ada@new.io'yes (users_email_key)irrelevantnot HOT — the entry's key itself must change

The HOT case, step by step:

  1. Descend users_pkey → 42 → (7,2); read heap page 7.
  2. Byte check: page 7's free space (1.2 KB, the gap between its line pointers and tuples) holds the ~100 B new version → HOT is on.
  3. Write v2 into page 7's free space under a new line pointer, lp5; stamp v1's xmax; v1's header now chains forward to (7,5).
  4. No index is touched. users_pkey and users_email_key still say … → (7,1..2); a reader arriving via either follows v1's chain one hop to v2, on the same page it already fetched.
  5. Later, once v1 is dead to everyone, any read of page 7 prunes it: v1's bytes are freed, lp2 becomes a redirect to 5. The indexes never learn any of this happened.
  6. The second row of the table is the same update on a crowded page: v2 goes to page 31, and both indexes must gain entries pointing at (31,1) — "fits on the same page" is nothing deeper than step 2 failing.
the levers, on this table
ALTER TABLE users SET (fillfactor = 90);   -- keep ~800 B/page free for step 2
SELECT n_tup_upd, n_tup_hot_upd FROM pg_stat_all_tables WHERE relname = 'users';

Indexes §09 — a DELETE's afterlife

Row id = 777 lives at (12,3), with entries in both indexes. Its death is a four-act story — after each act, note who still holds the corpse:

  1. DELETE FROM users WHERE id = 777; commit. Transaction 990 stamps xmax = 990 on the heap tuple. Nothing is removed anywhere.
  2. SELECT * FROM users WHERE id = 777; (after 990 is old news to every snapshot). The pkey descent still finds 777 → (12,3); the heap fetch finds the tuple dead to everyone; the scan returns 0 rows — and on its way out flips LP_DEAD on that entry's line pointer in the leaf.
  3. The same SELECT again. The descent reaches the entry, sees LP_DEAD, and skips the heap fetch entirely. Note the asymmetry: users_email_key learned nothing — hints are per-index, earned by whichever scan pays the wasted fetch.
  4. VACUUM users; runs the §09 flow: scan heap → dead TID list [(12,3), …]; scan users_pkey and delete matching entries; scan users_email_key and delete matching entries; only then free heap line pointer lp3. Freed space on every page is reusable in place; none of the touched pages unlinks unless it ended completely empty.

Indexes §10 — watching Heap Fetches move

The query needs only id — everything the pkey already stores — so the planner picks an index-only scan. Whether it actually skips the heap is decided per TID by the visibility map, and you can watch that decision flip:

psql — the same query, three moments
VACUUM users;                                    -- all VM bits set
EXPLAIN (ANALYZE) SELECT id FROM users WHERE id BETWEEN 100000 AND 100100;
 Index Only Scan using users_pkey on users …
   Heap Fetches: 0                               -- pure index answer

UPDATE users SET last_login = now() WHERE id = 100050;
                                                 -- clears the VM bit of heap page 1667
EXPLAIN (ANALYZE) SELECT id FROM users WHERE id BETWEEN 100000 AND 100100;
   Heap Fetches: 61                              -- every row living on page 1667

VACUUM users;                                    -- bit set again
EXPLAIN (ANALYZE) SELECT id FROM users WHERE id BETWEEN 100000 AND 100100;
   Heap Fetches: 0

What the scan did on each of the 101 entries it walked: read the TID's page number, look up that page's all-visible bit in the map (a cached lookup, no heap I/O). Bit set → emit id straight from the leaf entry. Bit clear → fall back to a normal heap fetch + snapshot check for that row — which is why one single-row UPDATE costs the scan 61 fetches: the rows were loaded in id order, so ~61 of the 101 ids share heap page 1667, and the page's bit vouches for all of them or none.

The moral in one line: Heap Fetches is the price of vacuum debt, paid by readers — 0 on a freshly vacuumed table, creeping up as writes clear bits, reset by the next VACUUM.
