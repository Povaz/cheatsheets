An index is a key → ctid map

Every PostgreSQL index is a secondary index: a physically separate relation — its own file, its own pg_class row — beside a heap that stores tuples in no particular order. An index tuple is nothing but a key plus a TID: (block, offset), the same pair you see as a row's ctid. The offset names a line pointer — the slot array at the top of the heap page — not the tuple bytes themselves; that one level of indirection is what every later trick (HOT, pruning) leans on.

1972: the B-tree contract

Bayer & McCreight's structure is a tree of pages, built for storage where each page is one I/O. Its invariants are the whole point:

  • Perfectly balanced — every leaf sits at the same depth, always.
  • Minimum occupancy — every node except the root stays at least half full, so depth is guaranteed logarithmic: a search costs O(log n) page reads no matter the data.
  • Sorted within a page — descent picks the child by comparing against the page's separator keys.

Balance is preserved by how the tree grows — never by rebalancing after the fact:

insertleaf page is full
splitdivide around the median, new right sibling
post upseparator inserted into the parent
cascadeparent full? split it too — up to the root
growroot splits → tree gains one level, everywhere at once

What PostgreSQL (and everyone) actually builds is Comer's B+ variant: interior pages hold separators only; every key → TID entry lives in the leaves; and the leaves are chained to their siblings. A range scan is one descent plus a walk along the leaf chain — the tree finds the start, the linked list does the rest.

1981: B-link — readers that survive splits

The concurrency problem: a reader takes a downlink toward a leaf while a writer splits that leaf — half its keys just moved to a new right sibling the parent doesn't point to yet. The classic cure, lock-coupling (hold the parent's lock until the child's is acquired), serializes traffic through the tree. Lehman & Yao's cure adds two fields to every page instead:

  • Right-link — every page points to its right sibling.
  • High key — every page states the upper bound of the keys it may contain.

A split moves keys right and leaves both fields correct. So a reader landing on a page checks its search key against the high key: too big means the page split under you — follow the right-link and check again. Move right until the high key covers your key. No coupling, no waiting on writers.

PostgreSQL's nbtree is this algorithm with deliberate deviations (the README spells them out):

  • Short read locks anyway — L&Y assumed each process reads a private copy of a page; a shared buffer pool breaks that, so readers take brief per-page locks while examining a page. Never more than a few at once — the move-right trick still removes coupling.
  • Left-links too — for backward scans, with their own move-left dance that L&Y never needed.
  • Suffix truncation — pivot tuples (separators and downlinks) drop attributes not needed to divide the key space; truncated positions mean "minus infinity". More fan-out, same invariants.
  • Deletion is grudging — only a completely empty page can be deleted, in two stages (half-dead, then unlinked), and the rightmost page of each level never is. B-trees split easily and shrink reluctantly.

The MVCC tax

Visibility lives only in the heap: xmin/xmax sit in the heap tuple header, and index entries know nothing about transactions. Core requires every index AM to hold one entry per row version. Both halves of that deal have consequences you meet at work:

  • Writes amplify. An UPDATE is a new heap version — and a new entry in every index of the table, keys changed or not. The escape is a HOT update: if no indexed column changed and the new version fits on the same heap page, no index is touched at all. The index keeps pointing at the original line pointer, which becomes a redirect to the live version; dead intermediate versions are pruned by ordinary page reads, no VACUUM required. (Lower fillfactor buys page room; pg_stat_all_tables counts HOT vs non-HOT.)
  • Deletes remove nothing. A dead row's index entries stay. A scan that discovers the corpse marks the entry LP_DEAD as a hint; real removal is VACUUM's job — which is why VACUUM must scan every index, and why index bloat is vacuum debt, not damage.
  • The index can't answer alone. Any TID an index returns must still be visibility-checked against the heap. The visibility map — one bit per heap page, "all rows here visible to everyone" — is the workaround: bit set, an index-only scan answers from the index; bit clear, it fetches the heap anyway. VACUUM sets the bits, so an index-only scan is only as fast as vacuuming is recent.

1995: the index became a plugin

The GiST insight: the shape of a height-balanced search tree — descend, insert, split, search — is generic. What varies per data type fits in four user methods:

  • Consistent — can this subtree possibly satisfy the query predicate?
  • Union — one predicate summarising everything under a page.
  • Penalty — how bad is it to push this new entry into this subtree?
  • PickSplit — how to divide an overflowing page in two.

Supply those and the tree machinery comes for free; B+-trees and R-trees both fall out as instances. That is the direct ancestor of every PostGIS, full-text and vector index. PostgreSQL generalises the same move into the index access method interface: an AM is a pg_am row exposing a table of callbacks, and core demands only the contract you already know — map keys to TIDs, one entry per row version, cooperate with VACUUM. Everything inside the index file is the AM's own business.

Shapes you declare on top

Orthogonal to the AM: four ways to shape what gets indexed. Each has one rule that decides whether the planner will actually use it.

ShapeDeclared asThe rule that decides usage
MulticolumnON t (major, minor)Equality on leading columns plus the first inequality bound the scanned range; trailing columns only filter inside the index. Skip scan can fake a leading equality when its distinct values are few. Beyond three columns, rarely helpful.
Partial… WHERE billed IS NOT TRUEUsed only when the query's WHERE provably implies the predicate — decided at plan time, so parameters that would match at runtime don't count. Also the way to a partial unique constraint.
ExpressionON t (lower(email))The query must repeat the same expression — WHERE lower(email) = …. The index stores the computed value.
CoveringON t (x) INCLUDE (y)Payload columns for index-only scans, invisible to uniqueness (UNIQUE stays on x alone). B-tree, GiST, SP-GiST.

1996: the other family — LSM

A B-tree updates in place: sooner or later every insert is a random page write. The LSM-tree refuses that trade — new entries land in a memory-resident component (C0) and migrate to disk components (C1…) through rolling merges: sequential, batched, cheap. The bill arrives on the read side — a lookup may probe every component — and as background compaction debt.

That is the single most important axis in modern storage engines: B-trees buy reads with expensive writes; LSM-trees buy writes with expensive reads. PostgreSQL sits firmly at the B-tree end; RocksDB and Cassandra at the other. Know the axis to know what PostgreSQL is not — and when a write-swamped table is fighting its engine, not your schema.
