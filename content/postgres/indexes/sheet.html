First, the heap: where rows actually live

A PostgreSQL table is stored as a heap: a plain file cut into fixed 8 KB pages. The page is the unit of I/O — PostgreSQL never reads or writes less than one page — so every cost question in this Sheet reduces to how many pages must be touched.

Inside a page, three regions share the 8 KB. A small page header sits first. Behind it grows an array of line pointers — tiny slots, one per row, each holding the byte offset of a row inside this page. The rows themselves — tuples — stack up from the far end of the page toward the middle. Free space is whatever gap remains between the two.

Two details planted here will run everything later:

  • The tuple header carries xmin and xmax — the IDs of the transaction that created this row version and the one that deleted it (empty while the row lives). Ignore them until the MVCC sections; just know they live in the heap tuple, nowhere else.
  • A row's address is the line pointer, not the bytes. Every row has a ctid — (page, slot) — where the slot names a line pointer. The tuple bytes can move around inside the page (compaction, cleanup) without the address changing, because only the line pointer's offset needs updating.

You can see the address on any row:

psql
SELECT ctid, id, email FROM users WHERE id = 42;
  ctid | id |      email
 ------+----+-----------------
 (7,2) | 42 | ada@example.com

Now the honest part of the name: a heap has no order. A new row lands in whatever page has room. So without help, WHERE id = 42 means a sequential scan — read every page, inspect every tuple. Fine for reading the whole table; hopeless for fetching one row out of millions. That gap is the entire reason indexes exist.

An index: a separate, sorted key → TID map

An index is a second structure beside the heap — its own file, its own pg_class row. Its entries are pairs: an index key (the column value) and a TID — (page, slot), exactly the pair you saw as ctid. An index entry contains nothing else: no row data, no transaction information. It is a map from value to heap address, kept in key order.

Every lookup through an index is the same four steps:

1 · descendfind the key in the index
2 · readtake the TID beside it
3 · fetchread that heap page, follow the line pointer
4 · checkconfirm the tuple is visible to your snapshot

Three facts to hold on to:

  • Every PostgreSQL index is secondary. The heap itself is never kept sorted — there is no clustered index as in some other systems. CLUSTER rewrites the table in index order once, but nothing maintains that order afterwards.
  • Indexes are a bargain, not a free lunch. Every INSERT must also insert into every index of the table. You are trading write work and disk space for read speed.
  • Step 4 is not optional. Why the index can never answer "is this row visible?" by itself is the story of the MVCC sections below.

Everything that follows is machinery for this map: making it fast (the B-tree), keeping it safe under concurrent writers (B-link), and keeping it honest under MVCC (versions, HOT, VACUUM, the visibility map).

B-tree: the map arranged as a tree of pages

The map needs a physical shape. A single sorted file would find keys in few reads (binary search) but dies on insert — making room in the middle means shifting everything after it. The B-tree (Bayer & McCreight, 1972) solves both at once by sorting within pages and putting a tree between pages. PostgreSQL builds the B+ flavour (Comer, 1979) that every database builds:

  • Leaf pages hold the actual key → TID entries, in key order.
  • Internal pages hold only separator keys and downlinks (pointers to child pages). They are signposts — no data lives there.
  • One root page sits on top.

A search for 42 descends: binary-search the root's separators to pick a downlink, repeat at each level, binary-search the leaf, read the TID. Cost = one page read per level.

Two invariants make that cost a guarantee, not a hope:

  • Perfect balance — every leaf sits at exactly the same depth, always.
  • Minimum occupancy — every page except the root stays at least half full, so the tree can never degenerate into something tall and thin: depth is logarithmic in the number of entries, worst case included.

The logarithm's base is the fan-out — entries per page — and it is huge. An 8 KB page holds a few hundred entries; call it 400. Two levels reach 160,000 keys, three reach 64 million, four reach 25 billion. Depth barely grows with the table — and since the root and internal levels are a tiny fraction of the index, they stay hot in shared buffers: a typical lookup does one or two real page reads.

Leaves are chained: ranges and order for free

Leaf pages are linked to their siblings (rightward and, in PostgreSQL, leftward too). Taken together, the leaf level is the entire key set as one sorted, doubly-linked list — the tree above it is just a fast way in. This turns one structure into an answer for whole families of queries:

  • Ranges — BETWEEN 40 AND 60 is one descent to the first key ≥ 40, then a walk along the chain until a key exceeds 60. No re-descents.
  • All the comparisons — < ≤ = ≥ > and IN are descents plus walks; that operator list is exactly what "B-tree" means to the planner.
  • Anchored LIKE — LIKE 'ann%' is secretly the range ['ann', 'ano'). A leading wildcard ('%son') gives the descent nothing to compare at the root, so it cannot use the tree. (Under a non-C locale this rewrite needs the text_pattern_ops operator class.)
  • ORDER BY — the walk emits rows already sorted: no Sort node, and ORDER BY … LIMIT 10 stops after ten entries. The left-links serve DESC the same way. This index-instead-of-sort trick is one of the biggest wins the planner has.

You can watch the sort disappear from a plan:

psql
EXPLAIN SELECT * FROM users ORDER BY created_at DESC LIMIT 10;
 Limit
   ->  Index Scan Backward using users_created_at_idx on users

Growth: pages split from the bottom up

An insert descends exactly like a search — there is only one leaf where the key belongs — and, if the leaf has room, places the entry in order. Done. The interesting case is a full leaf:

insertthe one correct leaf is full
splitdivide its keys near the middle; upper half moves to a new right sibling
post upa separator for the new page is inserted into the parent
cascadeparent full too? split it the same way — possibly up to the root
growroot splits → a new root above it — the tree gains one level, everywhere at once

Notice what is absent: there is no rebalancing step, ever. A root split is the only way the tree gets taller, and it deepens every path by one simultaneously — so all leaves stay at the same depth without anyone enforcing it after the fact. Balance is a by-product of how the tree grows.

Splits are also where the trouble lives: a split moves half a page's keys somewhere else while other backends may be mid-descent toward them. That is the next section.

B-link: readers that survive splits

The race, concretely: a reader examines the parent and picks the downlink toward the leaf that should hold 55. Before it gets there, a writer splits that leaf — the upper half of its keys, 55 included, just moved to a brand-new right sibling that the parent doesn't point to yet. The reader lands on the old page, finds no 55, and reports it missing. Not slow — wrong.

The classic cure is lock coupling: hold the parent's lock until the child's lock is acquired, so no split can slip in between. Correct, but every descent then contends for locks near the root — the tree's top becomes a bottleneck. Lehman & Yao (1981) found a way to make splits survivable instead of invisible, by adding two fields to every page:

  • Right-link — every page points to its right sibling.
  • High key — every page states the upper bound of keys it may contain.

A split updates both correctly: the old page keeps a right-link to the new sibling, and its high key becomes the split point. So a reader landing anywhere checks its search key against the page's high key. Too big? The page split under you — follow the right-link and check again. Move right until the high key covers your key. No coupling, no waiting on writers.

PostgreSQL's B-tree code (nbtree) is this algorithm with deliberate deviations — its README spells them out:

  • Short read locks anyway. Lehman & Yao assumed each process reads its own private copy of a page; PostgreSQL's shared buffer pool means a page could change while being examined, so readers take a brief per-page lock during examination — never more than a few at once. The move-right trick still removes the coupling.
  • Left-links too — for backward scans (ORDER BY … DESC), with their own move-left dance that L&Y never needed.
  • Suffix truncation — separator keys keep only the attributes needed to divide the key space; truncated positions read as "minus infinity". Smaller separators mean more of them per page: more fan-out, same invariants.
  • Deletion is grudging — only a completely empty page can be deleted, in two stages (marked half-dead, later unlinked), and the rightmost page of each level never is. B-trees split easily and shrink reluctantly — remember this when index bloat comes up below.

MVCC: UPDATE never updates

Now the second half of the story — what PostgreSQL's concurrency model does to this tidy picture. Under MVCC (multi-version concurrency control), writers never overwrite a tuple:

  • UPDATE writes a complete new version of the row elsewhere in the heap and stamps the old version's xmax.
  • DELETE just stamps xmax. Nothing is removed.
  • Every reader carries a snapshot and decides, per version, whether that version's xmin/xmax make it visible. Old versions stay because someone's snapshot may still need them — this is why readers never block writers.

All that machinery lives in the heap tuple headers from the first diagram. An index entry is still just key + TID — it knows nothing about transactions. From this one asymmetry, PostgreSQL derives the rule every index must obey: one index entry per row version, because any version might still be visible to someone. And its corollary: the index only ever returns candidates — step 4 of the lookup contract, the heap visibility check, has the final word.

You can watch a row move: the "same" row has a new address and a new creating transaction after an update.

psql
SELECT ctid, xmin, xmax FROM users WHERE id = 42;
 (7,2) |  951 |    0
UPDATE users SET last_login = now() WHERE id = 42;
SELECT ctid, xmin, xmax FROM users WHERE id = 42;
 (8,1) |  977 |    0        -- new version, new address

The dead versions this leaves behind — in the heap and in every index — are the subject of the next three sections: the escape hatch (HOT), the cleanup (VACUUM), and the workaround that lets indexes answer alone anyway (the visibility map).

HOT: the update that skips every index

First, feel the bill. A table with six indexes: one UPDATE of one row = one new heap tuple plus six index inserts — even if the updated column isn't in any index, because the new version has a new TID and every index must point at it. Six future-dead entries, too. This write amplification is the standing tax on indexed tables.

The escape is the HOT update (heap-only tuple). If both conditions hold:

  • no column used by any of the table's indexes changed (summarizing indexes — BRIN — don't count), and
  • the new version fits on the same heap page as the old one,

then no index is touched at all. The trick is the indirection from the first diagram: every index keeps pointing at the original line pointer. Inside the page, the old version links forward to the new one (a HOT chain), and a reader arriving via the index follows the chain to the live version. Once the old version is dead to everyone, its tuple bytes are dropped and its line pointer becomes a pure redirect — the address survives, the corpse doesn't.

Cleanup here doesn't even wait for VACUUM: any later read of the page — a plain SELECT — may prune the chain, removing dead intermediate versions and reclaiming their space, page-locally. Two practical levers follow directly:

  • A fillfactor below 100 reserves same-page room, making the "fits on the same page" condition more likely.
  • pg_stat_all_tables tells you whether you're getting the discount.
psql
SELECT n_tup_upd, n_tup_hot_upd FROM pg_stat_all_tables WHERE relname = 'users';

Deletes remove nothing: LP_DEAD and VACUUM

A DELETE stamps xmax and walks away. The heap tuple stays; every index entry pointing at it stays too. Commit doesn't clean up either — cleanup in PostgreSQL is always someone else's job, later. For indexes it happens in two tiers:

  • Opportunistic hints. An index scan that follows a TID and finds the tuple dead to every transaction marks the index entry LP_DEAD — "known dead" — on its way out. Later scans skip that pointless heap fetch, and the page may discard hinted entries when it needs the room. A scan paying a cost leaves a hint so the next scan doesn't.
  • The real collector: VACUUM. It gathers the heap's dead TIDs, then must scan every index of the table to remove the entries pointing at them — only then can the heap line pointers be freed, or an index entry would dangle. This is why VACUUM cost scales with index count, and why every index you add taxes the table's maintenance forever.

Index bloat is this system running behind: pages full of dead or removed entries. Recall from the B-link section that a page is deleted only when completely empty — sparse pages linger, so an index never slims down on its own. Bloat is vacuum debt, not damage; when the debt has compounded, REINDEX CONCURRENTLY rebuilds the tree tight.

Index-only scans and the visibility map

One tension is left. If the query needs only columns the index already stores — SELECT id FROM users WHERE id < 100 — the heap fetch looks redundant. But the versions section said visibility lives only in heap tuple headers, so skipping the heap should be impossible.

The workaround is the visibility map: one bit per heap page meaning "every tuple on this page is visible to every current and future transaction". Only VACUUM sets a page's bit; any write to the page clears it. The bit makes visibility a page-level question that can be answered without reading the page — the map is thousands of times smaller than the heap and stays cached.

index-only scanentry found in the index
VM bit?check the TID's page in the visibility map
setanswer straight from the index entry — zero heap I/O
clearheap fetch + visibility check — no saving for this row

So an index-only scan is fast in exact proportion to how recently the table was vacuumed. EXPLAIN (ANALYZE) reports the misses as Heap Fetches — on a freshly vacuumed table it reads 0; on a hot-updated one it can quietly degrade to an ordinary index scan.

psql
EXPLAIN (ANALYZE) SELECT id FROM users WHERE id BETWEEN 100 AND 200;
 Index Only Scan using users_pkey on users …
   Heap Fetches: 0

The AM family: an index is a plugin

Step back and notice how little of the preceding was demanded of the index, versus chosen by it. Core PostgreSQL requires exactly the contract you now know: map keys to TIDs · keep one entry per row version · cooperate with VACUUM. Everything inside the index file — page layout, tree shape, algorithms — is the index's own business. That makes an index type a plugin: an access method (AM), a row in pg_am exposing a table of callbacks, selected per index with CREATE INDEX … USING gin (…).

The insight behind this came from GiST (Generalized Search Tree, 1995): the machinery of a height-balanced tree — descend, insert, split — is generic; only four questions are data-type-specific:

  • Consistent — could this subtree possibly contain matches for the query?
  • Union — one predicate summarising everything under a page (the generalisation of "separator key").
  • Penalty — how bad would inserting this entry into this subtree be?
  • PickSplit — how to divide an overflowing page in two.

Answer those four for your data type and the balanced tree comes for free — B-trees and R-trees both fall out as instances. GiST is the direct ancestor of every PostGIS, full-text and vector index you have used. The built-in family:

AMStructureBuilt to answer
btreesorted balanced B-link tree (this Sheet)< ≤ = ≥ >, BETWEEN, IN, anchored LIKE, ORDER BY — the default for a reason
hashhash table: key's hash picks a bucket= and nothing else — hashing destroys order, so no ranges, no sorting
gistthe generalized balanced tree aboveoverlap, containment, distance — geometry, ranges; nearest-neighbour ORDER BY … <->
spgistspace-partitioned tree, non-balanced by design (quadtree, k-d, radix/trie)GiST's spirit for data that partitions rather than balances

Shapes you declare on top

Orthogonal to the AM choice: four ways to shape what gets indexed. Each comes with one rule deciding whether the planner will actually use it — and having seen the structure, every rule is now derivable rather than folklore.

The key one is multicolumn order. An index on (last_name, first_name) sorts like a phone book: by last name, then by first name within equal last names. So WHERE last_name = 'Verne' descends to one tight range — but WHERE first_name = 'Jules' alone is scattered through the whole book. First names are only sorted inside each last name; there is nothing to descend by.

ShapeDeclared asThe rule that decides usage — and why
MulticolumnON t (major, minor)Equality on leading columns plus the first inequality bound the descent range (the phone-book rule); trailing-column predicates only filter inside that range — they save heap trips but don't shrink the scan. A missing leading column with few distinct values can be faked by a skip scan: internally re-run the search once per value. Beyond three columns, rarely helpful.
Partial… WHERE billed IS NOT TRUEIndexes only the matching rows — a smaller tree. Used only when the query's WHERE provably implies the predicate, decided at plan time — so a parameter that would match at runtime doesn't count. Also the way to a unique constraint over a subset of rows.
ExpressionON t (lower(email))The leaf entries store the computed value — that's what the tree is sorted by — so the query must repeat the same expression: WHERE lower(email) = ….
CoveringON t (x) INCLUDE (y)Carries y as payload in the leaf entries so index-only scans can answer queries needing it — while keeping y out of the key: UNIQUE stays on x alone. B-tree, GiST, SP-GiST.

The other family: LSM, for contrast

One trait defines everything you just learned: the B-tree updates in place. An insert descends to the one correct leaf and rewrites that page, wherever on disk it happens to sit — so a write-heavy workload becomes a stream of random page writes scattered across the file.

The LSM-tree (log-structured merge-tree, 1996) refuses that trade. New entries land in a memory-resident component and migrate to disk through rolling merges into sorted runs — sequential, batched, cheap writes, never touching data in place. The bill moves to the read side: a lookup may probe the memory component and several disk runs, and the background merging (compaction) is standing debt.

That is the most important axis in modern storage engines: B-trees buy cheap reads with expensive writes; LSM-trees buy cheap writes with expensive reads. PostgreSQL sits firmly at the B-tree end; RocksDB and Cassandra at the other. Know the axis to know what PostgreSQL is not — and to recognise when a write-swamped table is fighting its engine rather than your schema.
