One process per connection

A running PostgreSQL server is a family of ordinary OS processes around one block of shared memory. The postmaster starts first: it allocates the shared memory, launches the background processes, and listens. Every client connection makes it fork a dedicated backend process — your session talks to that one process for its entire life, and max_connections (default 100) caps how many can exist. Run SELECT pg_backend_pid(); and you are looking at yours.

Shared buffers: every page goes through the pool

No backend reads a data file directly into private memory. All page traffic goes through shared buffers: an array of 8 KB slots in shared memory, plus a hash table mapping (relation, fork, page number) to a slot. Reading a page:

  1. Look up the page's tag in the buffer table. Hit → pin the slot ("in use — don't recycle") and read it. Done: no I/O at all.
  2. Miss → pick a victim slot by clock sweep: circle the pool decrementing each slot's usage count, and take the first unpinned slot at zero. Every pin bumps a slot's count, so recently-useful pages survive laps that evict idle ones.
  3. If the victim is dirty (modified since load), write it out first; then load the wanted page into the slot and pin it.

Writes are the same picture from the other side: a backend modifies the page inside the pool and marks the slot dirty — nothing is written to the data file at that moment, nor at commit. Dirty pages reach disk later, via the background writer (ahead of need) and the checkpointer (wholesale, periodically). Why a crash can't lose anything under this laziness is the last section. And PostgreSQL runs this cache itself rather than leaning on the OS's, because correctness will demand precise control over when a dirty page may reach disk.

From SQL text to a running plan

Inside your backend, a statement crosses four stages before any page is touched:

parsesyntax check; the text becomes a parse tree
rewriterules apply — above all, views are expanded into the base tables they hide
planenumerate the ways to compute the answer, cost each, keep the cheapest
executewalk the plan tree, pulling rows through it — this is what touches pages

The planner's inner life — statistics, join orders, cost formulas — deserves its own Sheet and is deliberately not this one. What matters here: with no indexes, the planner has exactly one way to read a table, and the executor's life is simple.

The sequential scan, procedurally

What the executor actually does for a filter on an unindexed column:

  1. Ask for every page of the table's main fork, 0 through N−1, in file order, each through the buffer pool.
  2. Big scans don't wipe the pool doing it: a large sequential scan recycles a private ring of ~256 KB of buffers instead of claiming fresh slots, so a million-row scan leaves the rest of the cache alone.
  3. Per page: walk the line pointers; for each normal tuple, check visibility against the query's snapshot (the picture of committed transactions the query started with — the Indexes Sheet §07 owns the full story), then evaluate the WHERE clause.
  4. Emit the survivors. There is no early exit — the last page might always hold one more match — unless a LIMIT is satisfied first.
psql — no index on email, yet
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM users WHERE email = 'ada@example.com';
 Seq Scan on users  (actual time=0.031..317.2 rows=1)
   Filter: (email = 'ada@example.com')
   Rows Removed by Filter: 999999
   Buffers: shared read=16667

The shape of the cost: 16,667 pages for one row — and 16,667 again next time, whatever the answer. Sequential reads are the cheap kind of I/O, but it is all of them, every time. Turning "look at everything" into "read four pages" is the Indexes Sheet, and it begins exactly here.

The write path: commit doesn't write your table

An INSERT, procedurally:

  1. Find room — ask the free space map (the Storage Sheet's _fsm fork) for a page with enough free space; none → extend the file with a fresh page.
  2. Write in memory — pin that page in the buffer pool, place the tuple in its free space, allocate its line pointer.
  3. Mark the buffer dirty. That is all: the data file itself is untouched.

UPDATE is the same plus one stamp: write a complete new version of the row (same page if it fits, any page with room otherwise) and set the old version's xmax — never overwrite in place. DELETE is the stamp alone. Why versions instead of overwrites is the Indexes Sheet's MVCC story.

So when COMMIT returns, the table's pages may be dirty in shared memory — and stay dirty for minutes. What makes that safe to promise:

WAL: why nothing is lost

The write-ahead log is the durability contract, and its one rule gives it its name: a change may reach the data files only after the log record describing it is safely on disk. From that rule, the whole write economy follows:

1 · changethe page is modified in shared buffers and marked dirty
2 · loga WAL record describing the change is appended to the WAL buffer
3 · commitflush only the WAL to disk — one sequential write; one fsync can commit many concurrent transactions at once
4 · laterthe checkpointer writes the dirty pages themselves; each checkpoint bounds how much log a crash would need
5 · crash?restart replays the WAL from the last checkpoint — roll-forward redo — and the lazy page writes are re-done from the log

The trade in one sentence: commits pay one sequential log flush instead of scattering every touched page to disk, because anything the crash takes from memory can be redone from the log. Checkpoints, full-page writes, and recovery mechanics earn their own future Sheet — this contract is all the earlier sections needed.
